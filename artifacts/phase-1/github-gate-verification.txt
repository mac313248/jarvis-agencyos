# Acceptance #45 — GitHub Merge-Gate Verification

Acceptance #45 (12_ACCEPTANCE_AND_IMPLEMENTATION.md): "Cursor builder cannot merge failed CI."

## What the workflow proves
`.github/workflows/phase-1.yml` proves a CI workflow EXISTS and runs the
Phase 1 checks (SOT guard, clean migrate, full suite) on push/PR to main
and to `phase-1/**` branches. The workflow YAML alone does NOT prove that a
failed/missing required CI check blocks merge to main. That requires a
GitHub branch-protection / ruleset enforcement, which is repository
configuration, not code.

      curl -sv https://api.github.com

api.github.com (the REST API). Branch protection / rulesets are configurable
ONLY via api.github.com. Therefore the builder CANNOT inspect or configure
branch protection from inside the Cursor sandbox, regardless of token
validity.

### Root cause (confirmed with runtime evidence)
The Cursor sandbox proxy returns HTTP 403 on CONNECT to api.github.com:443,
while github.com (git host) returns 200 and registry.npmjs.org returns 200
(see "Runtime evidence (debug session 30c27d)" above). `gh` validates the
keychain token and serves all REST/GraphQL via api.github.com, which is
blocked from the sandbox. So from inside the Cursor sandbox, `gh` reports the
keychain token as "invalid" and `gh repo view` returns Forbidden — NOT
because the owner's Mac Mini login is bad, but because the sandbox cannot
reach api.github.com. The builder also could not escape the sandbox
(required_permissions:["all"] was not granted), so it could not exercise the
host's keychain gh login to inspect or configure branch protection.

Per the owner's stop condition ("If, AFTER unsetting GH_TOKEN/GITHUB_TOKEN,
`gh auth status` still genuinely lacks access ... return WAITING_ON_OWNER
with the exact error"), #45 is WAITING_ON_OWNER. The owner is NOT asked to log
in again (the Mac Mini login is valid); the only blocker is that the
verification must run in a non-sandboxed environment where api.github.com is
reachable.

## Verifier repair (scripts/verify-github-gate.sh / verify-github-gate.mjs)
The first verifier printed a success-looking line ("configured branch
protection requiring ...") even after a GitHub API error. Repaired so that:
  - configuration success is printed only after the PUT succeeds;
  - a failed PUT exits nonzero;
  - the script never claims configuration succeeded after a GitHub API error;
  - final PASS is based on a successful readback confirming ALL of:
      * exact required check ("Phase 1 — Secure Core Spine / phase1");
      * strict=true;
      * enforce_admins=true;
      * force pushes disabled;
      * deletions disabled;
      * PR protection present.
  - idempotent: because branch protection is already configured, a normal
    future run is verification-only and does NOT rewrite the protection.

A unit test for the gate-evaluation logic lives at
tests/support/verifier-gate.test.mjs (outside the core `tests/*.test.mjs`
glob, so the core-spine suite stays at 41/41).
